# P4 Design Notebook

For P4, I reviewed every reaction for authentication and access control, finished two items left from P2, and polished the interface. Each entry explains a problem, what I changed and why, and how I confirmed it.

## 1. Reviewing Reactions and Access Control

I read all 17 endpoints and both cleanup reactions, and asked three questions of each: does it know who is asking, is that person allowed, and does every check run before the first change? Every endpoint turns the session cookie into an account first, so authentication was already consistent. Two endpoints had problems.

**1. A refused idea could still be created.**

*Problem.* My P2 notes found this and left it for P3: posting to a literary element outside the chart created the idea in Posting, but `Charting.addItem` refused to place it, so the idea existed, yet no one could see or delete it. The comment at the top of my composition even listed a `checkCell` gate, but it was never written, and `CreatePost` checked only the chapter.

*Change.* I added `Charting.checkCell(chart, row, column)`, which refuses unless both are in the chart, and `CreatePost` calls it in place of `checkRow`:

```
current session → checkMember → checkCell → checkReached → Posting.create → Charting.addItem
                  (refuse before any change)                 (changes)
```

*Why.* Every check now runs before the first change, which is the rule I set in P2.

*Check:* a concept test for `checkCell`, and a journey check that posting to a made-up literary element is refused and that the number of posts stays the same.

**2. A non-owner could find out which usernames are registered.**

*Problem.* Adding a member has two reactions on one endpoint: one adds a registered username, and the other refuses an unregistered one with `UNKNOWN_USER`. Only the first checked that the caller owns the chart. A member who wasn't the owner got `UNKNOWN_USER` for an unregistered name and `NOT_OWNER` for a registered one, so the two errors told them which accounts exist.

*Change.* I added `Charting.checkOwner(chart, owner)`, and the `UNKNOWN_USER` reaction calls it first. A non-owner now gets `NOT_OWNER` either way.

*Why.* An endpoint shouldn't tell someone anything if they aren't allowed to use it.

*Check:* a concept test for `checkOwner`, and a journey check that a non-owner adding an unregistered name gets `NOT_OWNER`.

**Reviewed, but not changed.**
- **Editing an idea and deleting a comment** check that the user is a member of the chart in the request, but not that the idea or comment is in that chart. Posting still refuses anyone but the author, so no one can change someone else's idea, and the fix needs a new Posting query to find a comment's post. I left it as a known limit.
- **Removing an upvote has no progress check,** on purpose: someone who moved their progress back can still take back an upvote.
- **Any member can add a literary element,** which P1 left open. I kept this, since the class, not only the teacher, finds new elements during discussion.

## 2. Showing a Chart's Members

*Problem.* My P2 notes listed a members list for P3, and testing P3 showed why: Millie could see the owner's name, but not her classmates, so she couldn't tell whether someone had been added. The owner couldn't check either, except by adding someone again and reading the error.

*Change.* I added a `Charting._members(chart)` query and put the members in the chart view. Chart Settings lists every member, marking the owner and "(you)," and the list updates as soon as the owner adds someone. The chart page shows "Owned by teacher · 4 members" under the title, linking to Chart Settings.

*Why.* The members come from the chart view, which only members can request, so members can see each other, outsiders can't, and no new access check was needed.

*Check:* a concept test that `_members` lists the owner and each added member, and screenshots of both pages.
